# Как LLM заговорила на трёх языках — полный разбор Части 3

## Смысл задачи, коротко

Confesor (отвечает на Makefile) и Oráculo (судит статьи) — это не заранее написанные фразы, а живой, творческий текст, который каждый раз генерирует LLM (Groq) заново. У предыдущих частей рефакторинга (хроника, уведомления) была задача "переводить готовые данные под язык зрителя при показе" — тут задача принципиально другая: нужно, чтобы сама модель писала на нужном языке в момент генерации, потому что творческий текст нельзя "перевести постфактум" без риска убить тон/шутку.

---

## Главный архитектурный вопрос — откуда backend вообще узнаёт, какой язык нужен

Это конкретный запрос одного юзера (не широковещательное фоновое событие, как было с AI-хроникой) — значит у нас есть точное знание "кто спрашивает и на каком языке" в момент самого запроса. Вопрос — как это знание физически доставить с фронта на бэк.

### Решение — стандартный HTTP-заголовок Accept-Language, а не свой велосипед

Это существующий, предназначенный именно для этого заголовок HTTP-протокола (браузеры сами его используют для указания предпочитаемого языка контента). Мы просто переиспользуем его — вместо того чтобы городить кастомное поле в теле каждого запроса, что пришлось бы отдельно добавлять в каждый DTO, каждую функцию API.

---

## Как заголовок доставляется — два разных механизма, потому что два разных способа делать запросы

### Механизм 1 — глобальный axios-interceptor (для всего, что идёт через apiClient)

```typescript
// api/client.ts
import i18n from '../i18n/i18n';

apiClient.interceptors.request.use((config) => {
  if (accessToken) {
    config.headers.Authorization = `Bearer ${accessToken}`;
  }
  config.headers['Accept-Language'] = i18n.language;
  return config;
});
```

Это тот же самый interceptor, что уже приклеивал JWT-токен к каждому запросу — мы просто добавили туда ещё одну строчку. Раз apiClient — это единая точка, через которую проходят почти все запросы приложения (кроме одного исключения, разберём ниже) — одна правка в одном файле автоматически чинит любой будущий эндпоинт, которому вдруг понадобится знать язык, без необходимости трогать десятки отдельных API-функций.

Важная деталь — `import i18n from '../i18n/i18n';` напрямую, не через React-хук useTranslation(). client.ts — обычный TypeScript-модуль, не React-компонент, там не может быть хуков. i18next устроен так, что его "инстанс" (объект i18n) — обычный JS-объект с полем .language, доступный откуда угодно в коде, не только изнутри React-компонентов через хук.

### Механизм 2 — вручную, для streamConfession (потому что там сырой fetch, не axios)

```typescript
// api/ai.ts
const response = await fetch('/api/ai/confess', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Accept-Language': i18n.language,
    Authorization: `Bearer ${getAccessToken()}`,
  },
  ...
});
```

Помнишь, почему streamConfession вообще использует fetch, а не наш apiClient? Мы разбирали это ещё в самом начале работы над Confesor — axios в браузере буферизует весь ответ целиком, прежде чем отдать его коду, а нам нужен потоковый доступ к чанкам по мере поступления (эффект "печатающегося" текста). Раз это не apiClient — наш новый interceptor физически не может сработать здесь, приходится прописывать заголовок руками, в этом одном конкретном месте.


`@Headers('accept-language')` — декоратор NestJS, вытаскивающий значение конкретного HTTP-заголовка прямо в переменную метода, тем же способом, что `@Body()` вытаскивает поля из тела запроса. Заголовки регистронезависимы по HTTP-стандарту, поэтому неважно, что фронт отправил Accept-Language с заглавных букв — NestJS находит его, даже указав в декораторе accept-language строчными.

То же самое сделано в articles.controller.ts для create и update.

## Защита от "а что если заголовка нет или там мусор" — resolveLanguage

```typescript
type Language = 'es' | 'en' | 'ar';

function resolveLanguage(language?: string): Language {
  return language === 'en' || language === 'ar' ? language : 'es';
}
```

Простая, но важная функция — гарантирует, что мы никогда не попытаемся обратиться к несуществующему ключу в объекте промптов. Если заголовок вообще отсутствует (старый клиент, ручной запрос через curl без заголовка, что угодно) — по умолчанию используется испанский. Если заголовок есть, но там что-то странное (например fr — язык, которого у нас нет) — тоже фолбэк на испанский. Только 'en' и 'ar' проходят как есть, всё остальное превращается в 'es'.

## Сами промпты — три версии, объект-словарь вместо одной строки

```typescript
const SYSTEM_PROMPTS: Record<Language, string> = {
  es: `Eres el Confesor de La Iglesia del Verdadero Relink...`,
  en: `You are the Confessor of La Iglesia del Verdadero Relink...`,
  ar: `أنت المعترف في "كنيسة إعادة الربط الحقيقية"...`,
};
```

Дальше просто:
```typescript
const lang = resolveLanguage(language);
...
messages: [{ role: 'system', content: SYSTEM_PROMPTS[lang] }, ...]
```

То же самое сделано для ARTICLE_CHECK_PROMPTS (Oráculo).

Важно, что это не механический перевод одной фразы на три языка — каждый промпт заново сформулирован так, чтобы результат звучал естественно именно на этом языке (сохраняя тот же тон — торжественный, драматичный, слегка саркастичный средневековый священник), а не был дословной калькой с испанского синтаксиса.

## Самая хитрая деталь всей Части 3 — вердикт Oráculo остаётся на испанском всегда

Промпт Oráculo просит модель ответить строго определённым протоколом: первая строка — слово APROBADO или RECHAZADO, и наш backend-код потом парсит этот ответ, ища именно эти конкретные слова:

```typescript
const approved = normalized.startsWith('APROBADO');
```

Если бы мы перевели и эти протокольные слова на английский/арабский ("APPROVED"/"REJECTED", "مقبول"/"مرفوض") — пришлось бы дублировать логику парсинга на три языка, что хрупко и подвержено ошибкам (что если модель на арабском промпте вдруг всё равно ответит по-испански, по привычке?).

Решение — явно прописано в самом промпте, на всех трёх языках:

```
First line: the word APROBADO or RECHAZADO (always in Spanish, exactly
as written here — this is a fixed protocol marker, do not translate
it), and nothing else on that line.
```

Меняется только текст причины отказа (вторая строка) — она пишется на запрошенном языке. Слова-маркеры APROBADO/RECHAZADO — это техническая часть протокола связи между нами и моделью, не часть контента, который видит юзер напрямую (юзер видит только текст причины, не сам служебный маркер) — поэтому их не нужно переводить, и парсинг на бэкенде остаётся одинаковым независимо от языка, не завязанным на три разных набора ключевых слов.

## Побочно найденный и исправленный баг — ai.controller.ts

При правке этого файла заметила: обработка ошибок использовала error.message вместо error.getResponse():

```typescript
// Было (хрупко для наших новых ошибок-объектов)
const message = error instanceof HttpException ? error.message : 'Error interno';

// Стало (правильный, официальный метод NestJS)
const body = error instanceof HttpException ? error.getResponse() : { statusCode: 500, message: 'Error interno' };
res.status(status).json(body);
```

Раз мы (в Части 2) поменяли ошибки с обычных строк на объекты ({code: 'CONFESSOR_RATE_LIMITED'}), error.message больше не гарантированно содержит то, что мы реально туда положили. getResponse() — это специально предназначенный метод HttpException именно для того, чтобы получить точно тот объект/строку, что был передан в конструктор — надёжнее, чем полагаться на побочное поведение .message.

## Полная схема — путь одного запроса от клика до ответа на нужном языке

1. Юзер переключает язык на английский через LanguageSwitcher → i18n.language становится 'en'
2. Юзер пишет Makefile, жмёт "Confess" → streamConfession() в api/ai.ts строит fetch-запрос, вручную добавляя Accept-Language: en
3. Запрос долетает до AiController.confess, @Headers('accept-language') извлекает 'en'
4. AiService.streamConfession(makefile, 'en') → resolveLanguage('en') возвращает 'en' как есть
5. SYSTEM_PROMPTS['en'] выбирается, отправляется в Groq вместе с содержимым Makefile
6. Groq генерирует ответ на английском, соблюдая тон и лимит длины из промпта
7. Ответ стримится обратно чанками через тот же HTTP-response, ConfesionarioPage показывает его "печатающимся" на экране — уже на английском, без какого-либо постобработки/перевода на фронте

Для Oráculo (статьи) — идентичная логика, только через apiClient (interceptor приклеивает заголовок автоматически) и без стриминга (один финальный ответ вместо потока).
