# Библиотека статей — полный разбор от начала до конца

## Общая картина и ключевое архитектурное решение

Мы разбирали два варианта: загружать готовые файлы (`.pdf`/`.docx`) или писать прямо на портале. Выбрали второе — потому что цель была не "хранилище документов", а реальный, читаемый прямо на сайте текст, который можно показать на странице статьи, вытащить случайные три для виджета на `/celda`, и — важно — скормить в LLM для проверки темы. Загруженный файл пришлось бы сначала распарсить (новые библиотеки, новые точки отказа) просто чтобы получить тот же самый текст — бессмысленное усложнение.

Второе ключевое решение — раз ты сказал "не нужен отдельный черновик", схема получилась проще некуда: у статьи нет поля "опубликована/нет". Она либо существует в БД (значит уже прошла проверку и опубликована), либо не существует вообще (отклонена, ничего не сохранилось). Само действие "создать запись в БД" и "опубликовать" — это одно и то же действие, а не два разных состояния одной сущности.

## Backend, часть 2 — проверка темы через LLM

### Почему непотоковый вызов, а не `stream: true`

```typescript
async checkArticleRelevance(title: string, content: string) {
  const completion = await this.groq.chat.completions.create({
    model: MODEL_NAME,
    messages: [...],
    max_tokens: 150,
  });
  ...
}
```

Помнишь Confesor-бота — там `stream: true`, потому что ответ печатается на экране постепенно, юзер видит текст по мере генерации. Тут — совсем другая задача: нам нужен один окончательный вердикт ("да" или "нет"), прежде чем решить, сохранять статью или нет. Нет смысла "печатать" вердикт по буквам — мы всё равно должны дождаться всего ответа целиком, прежде чем принять решение, так что `stream` тут только усложнил бы код без пользы.

### Текстовый протокол вместо JSON — осознанный выбор

Промпт просит модель ответить в строгом формате:
```
Primera línea: la palabra APROBADO o RECHAZADO
Segunda línea: (если RECHAZADO) причина
```

Разбор ответа:
```typescript
const lines = raw.split('\n');
const verdict = lines[0]?.trim().toUpperCase();
const approved = verdict === 'APROBADO';
```

Почему не попросили модель вернуть JSON (`{"approved": true, "reason": "..."}`)? LLM без специального "JSON mode" не всегда строго соблюдают структуру JSON — если модель добавит лишний символ, пропустит кавычку, `JSON.parse` упадёт с ошибкой. Простой текстовый протокол "первая строка — вердикт, дальше — текст" гораздо устойчивее к небольшим отклонениям модели от точного формата — даже если модель на что-то не так среагирует, `lines[0]` почти наверняка всё равно будет либо "APROBADO", либо чем-то, что просто не совпадёт и даст `approved: false` (то есть система "ошибается в сторону строгости", а не падает с исключением).

### Важно — проверка происходит ДО сохранения в БД

```typescript
const check = await this.aiService.checkArticleRelevance(dto.title, dto.content);
if (!check.approved) {
  throw new BadRequestException(check.rejectionMessage);
}
const article = await this.articlesService.createArticle(...);
```

Порядок операций тут принципиален: если LLM отклонила статью — код даже не пытается сохранить её в БД, выбрасывает исключение сразу. Отклонённая статья физически никогда не существовала в базе данных — это прямое следствие решения "нет черновика": раз нет промежуточного состояния, момент проверки и момент сохранения слиты в одну неразрывную последовательность.

## Backend, часть 3 — случайная выборка статей, два шага вместо одного

```typescript
async getRandomArticles(count: number) {
  const allIds = await this.prisma.article.findMany({ select: { id: true } });
  if (allIds.length === 0) return [];

  const shuffled = [...allIds].sort(() => Math.random() - 0.5);
  const pickedIds = shuffled.slice(0, count).map((a) => a.id);

  return this.prisma.article.findMany({
    where: { id: { in: pickedIds } },
    include: AUTHOR_SELECT,
  });
}
```

Почему два запроса к БД, а не один `ORDER BY RANDOM() LIMIT 3`? У Prisma нет прямого встроенного способа сказать "отсортируй случайно" в конструкторе запросов (в отличие от чистого SQL, где `ORDER BY RANDOM()` — стандартная конструкция PostgreSQL). Обходной путь: сначала достаём только ID всех статей (дёшево — это просто числа, не тексты статей целиком), перемешиваем их в памяти Node.js через `.sort(() => Math.random() - 0.5)`, берём первые `count` штук, и только затем делаем второй запрос — достаём полные данные (заголовок, текст, автор) только для выбранных ID.

`.sort(() => Math.random() - 0.5)` — простой (хоть и не идеально статистически честный для больших массивов) способ перемешать массив: функция сравнения возвращает случайное число между -0.5 и 0.5, заставляя `.sort()` расставлять элементы в непредсказуемом порядке.

## Backend, часть 4 — порядок роутов, снова

```typescript
@Get('random')  // ← должен быть ПЕРЕД :id
async getRandom(@Query('count') count?: string) { ... }

@Get(':id')
async getOne(@Param('id', ParseIntPipe) id: number) { ... }
```

Та же самая закономерность, что мы уже проходили десяток раз (`/users/me` перед `/users/:id`, `/notifications/read-all` и т.д.) — параметризованный роут `:id` совпадает с любым текстом на этом месте URL, включая слово `"random"`. Если бы порядок был обратным — запрос на `/articles/random` попытался бы интерпретировать `"random"` как число через `ParseIntPipe` и упал бы с ошибкой.

### Двойная защита на создание статьи

```typescript
@Controller('articles')
@UseGuards(JwtAuthGuard)   // ← на уровне класса: нужен логин для ВСЕХ методов
export class ArticlesController {
  ...
  @Post()
  @UseGuards(RolesGuard)    // ← дополнительно, только для этого метода
  @Roles('INQUISIDOR', 'ARZOBISPO')
  async create(...) { ... }
}
```

`JwtAuthGuard` на уровне класса — просто "нужно быть залогиненным" для любого действия с этим контроллером (читать статьи может каждый). `RolesGuard` — дополнительный guard, навешанный только на конкретный метод `create` — сужает доступ ещё сильнее, именно для публикации. NestJS применяет оба guard'а последовательно для этого конкретного метода — оба должны пропустить запрос, чтобы код внутри выполнился.

## Backend, часть 5 — попутно найденные и исправленные баги

`AiModule` не экспортировал `AiService` — без `exports: [AiService]` в модуле, `ArticlesModule` физически не мог бы инжектировать этот сервис к себе, несмотря на `imports: [AiModule]` — NestJS требует явного разрешения "делиться" провайдером с другими модулями.

Забытый временный rate-limit — в комментарии кода прямым текстом было написано "TEMPORAL para pruebas... Volver a limit: 5 después de probar" — забытая заметка от прошлого тестирования, ограничивающая Confesor-бота одним запросом в минуту вместо нормальных пяти. Раз мы теперь тоже используем этот модуль (для проверки статей), с лимитом `1` тестирование стало бы мучительным — вернула на `5`.

## Frontend, часть 3 — `ArticlesListPage`

### Функция обрезки текста

```typescript
function excerpt(content: string, maxLength = 180): string {
  if (content.length <= maxLength) return content;
  return content.slice(0, maxLength).trim() + '…';
}
```

Простая "чистая" функция (не хук, не компонент) — обрезает длинный текст статьи до превью в списке, добавляя многоточие только если реально что-то обрезала.

### Проверка права на "Escribir un tratado"

```typescript
const MODERATOR_ROLES = ['INQUISIDOR', 'ARZOBISPO'];
...
setCanWrite(MODERATOR_ROLES.includes(me.data.role));
```

Это клиентская проверка — определяет, показывать ли кнопку вообще. Реальная защита — на бэкенде (`@Roles('INQUISIDOR', 'ARZOBISPO')`), эта фронтовая проверка чисто про UX (не показывать бессмысленную кнопку тому, кто всё равно получит `403` при попытке ей воспользоваться).

## Frontend, часть 4 — `ArticleDetailPage`

```tsx
{article.content.split('\n').filter(Boolean).map((paragraph, i) => (
  <p key={i}>{paragraph}</p>
))}
```

Текст статьи хранится в БД одной строкой (с переносами `\n` внутри, там где юзер нажимал Enter при написании). `.split('\n')` — разбивает на массив строк-абзацев. `.filter(Boolean)` — убирает пустые строки (если юзер случайно дважды нажал Enter подряд, между абзацами была бы пустая строка, превращающаяся в пустой `<p></p>`, которого мы не хотим). Каждый непустой абзац оборачивается в собственный `<p>`.

## Frontend, часть 5 — `NewArticlePage`, обработка ошибки от LLM

```typescript
try {
  const article = await createArticle(title.trim(), content.trim());
  navigate(ROUTES.ARTICLE(article.id));
} catch (err) {
  const message =
    (err as { response?: { data?: { message?: string | string[] } } })?.response?.data
      ?.message ?? 'El Inquisidor ha rechazado esta petición.';
  setError(Array.isArray(message) ? message.join(', ') : message);
}
```

Тот же приём type assertion, что мы применяли в `ConfesionarioPage` — вытаскиваем текст ошибки прямо из тела ответа axios. `message?: string | string[]` — NestJS иногда возвращает массив строк вместо одной (если несколько правил валидации сработали одновременно, например и заголовок слишком короткий, и текст слишком длинный) — `Array.isArray(message) ? message.join(', ') : message` аккуратно обрабатывает оба случая одной строкой кода.

### Кнопка недоступна, пока условия не выполнены

```tsx
<Button
  disabled={isPublishing || title.trim().length < 3 || content.trim().length < 50}

```

Клиентская защита от заведомо невалидной отправки — если заголовок/текст ещё слишком короткие, кнопка физически неактивна, юзер не тратит время на запрос, который бэкенд всё равно отклонит валидацией DTO.

## Frontend, часть 6 — маршрутизация, снова та же закономерность

```tsx
{/* /biblioteca/nueva ПЕРЕД /biblioteca/:id */}
<Route path="/biblioteca/nueva" element={...} />
<Route path="/biblioteca/:id" element={...} />
```

Тот же самый принцип, что мы применяли на бэкенде для порядка роутов (`/users/me` перед `/users/:id`) — теперь применённый и на фронтенде, в React Router. React Router проверяет маршруты в порядке объявления, и `:id` мог бы перехватить `/biblioteca/nueva`, если бы стоял раньше.

## Итоговая схема — полный путь одной статьи

1. `INQUISIDOR` заходит на `/biblioteca`, жмёт "Escribir un tratado" (кнопка видна только благодаря клиентской проверке роли)
2. Заполняет форму, жмёт "Publicar" → `POST /articles`
3. Backend сначала отправляет текст в Groq на проверку темы (`checkArticleRelevance`) — ничего ещё не сохранено
4. Если LLM говорит "RECHAZADO" → бэкенд возвращает `400` с текстом выговора → фронт показывает его прямо в форме, статья исчезает бесследно, юзер может исправить и попробовать снова
5. Если "APROBADO" → статья сохраняется в БД → создаётся запись в публичной хронике (`createArticlePublishedEvent`) → юзера перекидывает на страницу свежесозданной статьи
6. На `/celda` у всех юзеров виджет `RandomArticles` при следующей загрузке страницы может подхватить свежую статью в свою случайную тройку (`getRandomArticles` перевыбирает заново при каждом рендере компонента)
7. Любой юзер может открыть `/biblioteca`, увидеть статью в общем списке с превью, кликнуть — попасть на `/biblioteca/:id`, прочитать целиком
