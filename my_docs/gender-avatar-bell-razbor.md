# Пол, склонение роли, дефолтная аватарка, колокольчик — полный разбор

## С чего всё начиналось — три отдельные задачи

1. При регистрации выбираем пол (Hermano/Hermana) → роли отображаются в правильном роде (HERMANA/INQUISIDORA/ARZOBISPA для женщин)
2. Дефолтная аватарка для всех + кнопка её удаления (возврат к дефолту)
3. Колокольчик уведомлений приглушается, если уведомлений нет

Плюс по пути вылезло два реальных бага, которые мы отдельно продиагностировали и починили — разберём и их тоже.

## Часть 1 — пол и склонение роли

### Ключевая архитектурная идея — роль и её отображение разделены

Самое важное решение всей этой работы: роль (`HERMANO`/`INQUISIDOR`/`ARZOBISPO`) — это техническое значение, определяющее права доступа, и оно никогда не должно зависеть от пола. Отдельно от этого — отображение роли на экране, которое должно учитывать пол (мужская или женская форма слова). Мы намеренно не стали городить отдельный enum вида `HERMANO_M`/`HERMANO_F` — это раздуло бы всю систему прав вдвое. Вместо этого — одна маленькая чистая функция, превращающая `(роль, пол)` → `текст для показа`.

### Схема БД

```prisma
enum Gender {
  MASCULINO
  FEMENINO
}

model User {
  ...
  role   Role   @default(HERMANO)
  gender Gender @default(MASCULINO)
  ...
}
```

`@default(MASCULINO)` — важная деталь: раз мы добавляем новое обязательное поле в таблицу, где уже могли быть строки (существующие юзеры) — Prisma требует знать, каким значением заполнить это поле у уже существующих записей. Дефолт решает эту проблему технически, хотя по факту при регистрации юзер всегда явно выбирает пол через форму — дефолт тут скорее "страховка на случай миграции", чем реальный сценарий использования.

### Утилита склонения — сделана дважды, по одной на каждую сторону

```typescript
const FEMININE_FORMS: Record<string, string> = {
  HERMANO: 'HERMANA',
  INQUISIDOR: 'INQUISIDORA',
  ARZOBISPO: 'ARZOBISPA',
};

export function getGenderedRole(role: string, gender: string): string {
  if (gender === 'FEMENINO') {
    return FEMININE_FORMS[role] ?? role;
  }
  return role;
}
```

Живёт в двух местах: `backend/src/common/gendered-role.ts` и `frontend/src/utils/genderedRole.ts` — практически идентичный код. Почему не один общий файл? Backend и frontend — это два разных приложения, каждое со своей отдельной сборкой (NestJS компилирует одно, Vite — другое), между ними в этом проекте нет общего "shared"-пакета кода — пришлось буквально продублировать тот же короткий кусок логики дважды.

Зачем вообще нужна версия на backend, если вся "красота" отображения — дело фронта? Потому что публичная хроника (`CommunityEvent`) хранит уже готовый, отрендеренный текст в базе данных (например "X ha alcanzado el rango de..."). Этот текст нельзя пересчитать заново на фронте после того, как он уже сохранён строкой — значит склонение нужно применить в момент создания этой строки, то есть на backend.

### `Record<string, string>` — что это за тип

`FEMININE_FORMS: Record<string, string>` — TypeScript-тип "объект, где любой строковый ключ ведёт к строковому значению" — по сути типизированный аналог JS-объекта-словаря. `FEMININE_FORMS[role] ?? role` — пробуем найти значение по ключу; если роли нет в словаре (такого не должно случиться, но на всякий случай) — просто возвращаем исходную роль без изменений, через `??`.

### Куда пришлось "протащить" `gender`

Оказалось, что это поле нужно везде, где раньше передавалась `role` — потому что без пола рядом с ролью склонение просто невозможно вычислить. Список мест:

Backend:
- `RegisterDto` — новое поле с валидацией `@IsIn(['MASCULINO', 'FEMENINO'])`
- `AuthService.register` — передаёт `dto.gender` при создании юзера
- `UsersService` — `gender` добавлен в оба select'а (свой профиль, публичный профиль)
- `AdminService.listUsers`/`changeRole` — добавлен `gender` в select
- `ChatService` — `gender` добавлен в select того, кто удалил сообщение (`deletedBy`), не в `sender` (там пол не нужен)
- `AdminController.changeRole` — применяет `getGenderedRole` к тексту уведомления и записи в хронике

Frontend:
- Все интерфейсы, где раньше было поле `role` (`Profile` в `HomePage`, `PublicProfile` в `api/users.ts`, `AdminUser` в `api/admin.ts`, `Message.deletedBy` в `api/chat.ts`) — добавлено поле `gender`
- `RoleBadge` — теперь принимает два пропа (`role`, `gender`) вместо одного, вычисляет склонённый текст внутри себя
- `AdminPage` — в выпадающем списке `<select>` текст пункта (`<option>`) склонён под пол конкретного юзера в строке, а значение (`value`), которое реально отправится на сервер при выборе — остаётся техническим, несклонённым
- `ChatPage` — плашка удалённого сообщения использует `getGenderedRole(deletedBy.role, deletedBy.gender)`

### Форма регистрации — почему radio, а не checkbox

Изначально ты сказал "чекбокс", но для выбора ровно одного варианта из двух взаимоисключающих правильный HTML-элемент — `<input type="radio">`, не `<input type="checkbox">` (чекбоксы — для независимых вкл/выкл, не для "выбери один из двух"). Разница смысловая, не просто вкусовщина.

`className="sr-only"` — Tailwind-класс "screen-reader only": визуально прячет элемент (не через `display:none`, который убрал бы его и из доступности для скринридеров, а специальным CSS-приёмом, оставляющим элемент "видимым" для вспомогательных технологий и клавиатурной навигации). Мы используем его, чтобы спрятать настоящий `<input type="radio">`, при этом стилизуя окружающий `<label>` как красивую кликабельную "таблетку".

Финальный дизайн переключателя — "капсула внутри капсулы": внешний `<div>` с `rounded-full` и рамкой, `p-1` (небольшой отступ внутри), и внутри — активный `<label>` тоже получает `rounded-full` с золотым фоном, создавая эффект плавающего внутри рамки выделения активного варианта.

## Часть 2 — дефолтная аватарка

### Упрощение компонента `Avatar`

Было — две ветки: `<img>`, если аватарка есть, или кружок с первой буквой имени, если нет. Стало — всегда `<img>`, просто `src` выбирается через `??`:

```tsx
<img src={avatarUrl ?? '/default-avatar.png'} ... />
```

Компонент стал проще, а не сложнее — убрали целую условную ветку разметки, заменив её одним `??` в атрибуте.

### Удаление аватарки — почему это не требует ничего "особенного" технически

```typescript
async removeAvatar(userId: number) {
  return this.prisma.user.update({
    where: { id: userId },
    data: { avatarUrl: null },
    select: SELF_PROFILE_SELECT,
  });
}
```

Всё, что делает "удаление" — ставит `avatarUrl` обратно в `null`. Раз `Avatar`-компонент уже сам умеет показывать дефолтную картинку, когда `avatarUrl` пустой — никакой дополнительной логики "назначить дефолтную аватарку конкретному юзеру" не требуется вообще, дефолт всегда один и тот же статичный файл, лежащий во фронтенде (`public/default-avatar.png`), а не что-то, что нужно копировать/привязывать к каждому юзеру индивидуально на диске сервера.

### Порядок роутов — снова та же история

`DELETE 'me/avatar'` в контроллере объявлен до `GET ':id'` — та же логика, что мы разбирали для `/users/me` много раз: параметризованный роут (`:id`) мог бы случайно "перехватить" запрос, предназначенный для точного текстового пути, если бы порядок был обратным.

## Часть 3 — приглушение колокольчика

```tsx
className={`relative text-xl transition-colors ${
  notifications.length === 0
    ? 'text-cream-400/40 hover:text-cream-400'
    : 'text-cream-100 hover:text-gold-500'
}`}
```

`text-cream-400/40` — Tailwind-синтаксис "цвет с прозрачностью": слэш и число после названия цвета задают его непрозрачность в процентах (тут — 40%). Простой способ приглушить элемент, не заводя для этого отдельный новый цвет в палитре.

Условие — `notifications.length === 0` (уведомлений вообще нет, а не "все уже прочитаны") — именно та интерпретация, которую ты просил.

## Отладочная сага — два реальных бага, найденных по пути

### Баг 1 — недобитые упоминания `GUARDIAN`

После переименования роли в `INQUISIDOR` в двух местах остались забытые старые упоминания:

```typescript
// ChatPage.tsx
const isModerator = ownRole === 'GUARDIAN' || ownRole === 'ARZOBISPO';

// AdminPage.tsx
const ROLES: Role[] = ['HERMANO', 'GUARDIAN', 'ARZOBISPO'];
```

Как нашли: простой `grep -rn "GUARDIAN" frontend/src backend/src` — быстрый, надёжный способ убедиться, что переименование прошло действительно везде, а не полагаться на память/визуальный осмотр каждого файла.

Почему это конкретно вызывало симптом "Guardian в выпадающем списке" — раз `ROLES` содержал строку `'GUARDIAN'`, а не `'INQUISIDOR'`, наша функция `getGenderedRole('GUARDIAN', gender)` не находила такого ключа в словаре `FEMININE_FORMS` (там ключи — актуальные `INQUISIDOR`) и просто возвращала входную строку как есть — отсюда и "Guardian" на экране вместо правильного склонённого варианта.

### Баг 2 — забытая миграция БД

```
PrismaClientKnownRequestError: The column `User.gender` does not exist in the current database.
```

Причина: мы добавили поле `gender` в `schema.prisma` (файл-описание того, какой должна быть структура БД), но забыли выполнить `make db-migrate-dev name=add_gender` — команду, которая реально меняет структуру таблицы в PostgreSQL. Схема "на бумаге" и реальная база разошлись.

Диагностика:
```bash
docker compose exec backend npx prisma migrate status
```
Показала "Database schema is up to date!" — но это означало "актуальна относительно существующих файлов миграций", а не "актуальна относительно `schema.prisma`". Ключевая проверка — простой просмотр списка папок в `prisma/migrations/` и сверка "а есть ли там вообще миграция про `gender`?" — её не было.

Фикс: ровно та команда, которую пропустили изначально — `make db-migrate-dev name=add_gender`.

### Общий урок с обоими багами

Оба бага — классический пример того, что простая, механическая проверка (grep по кодовой базе, просмотр списка файлов миграций) находит проблему быстрее и надёжнее, чем попытки "угадать" причину по симптомам. Когда несколько разных мест одновременно ведут себя странно — стоит в первую очередь заподозрить одну общую причину (не применённые изменения, не выполненный шаг), а не начинать чинить каждый симптом как отдельный, самостоятельный баг.
